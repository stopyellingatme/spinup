# Writing the docs

These rules keep the spinup docs easy to read.
Read them before you add or change a page.

## The reader

The reader is a developer who wants to do one thing now.
They scan the page for an example, copy it, and change it.
They read the prose only when the example is not enough.

So every page answers three questions, in this order:

1. What is this, and when do I use it?
2. What do I type? (an example)
3. What else can I change? (options, tables, details)

## The shape of a page

Use this shape for a guide. Leave out a section that has nothing to say.

````markdown
---
title: Audit trail
parent: Build your app
nav_order: 8
---

# Audit trail

One or two sentences: what this gives you and when you want it.

```console
$ spinup module add audit
```

## How it works        <- short, only what the reader needs to use it
## <Task 1>            <- a heading that names a task: "Show the history of a record"
## <Task 2>
## Reference           <- tables of flags, keys, and defaults
## Troubleshooting     <- symptom, cause, fix
## See also            <- 2 to 5 links
````

A command page in `docs/commands/` uses the same shape.
Its first example is the most common use of the command.

## Examples

- Put a working example in the first screen of every page.
- Give each command, flag group, and configuration key an example.
- Keep an example short. Show the smallest input that does the job.
- Show the output when the output helps the reader. Use `...` to hide long output.
- Use the same example app on a page. Prefer `todo` with the module `example.com/todo`.

Console blocks run in CI (`make doctest`).
A `$` line is a command, and the lines after it are the expected output.
`...` matches any lines.

If a block needs a VM, a cloud account, Docker, or the network, put this line before it:

```markdown
<!-- doctest: skip -->
```

If a block needs an environment variable, use `<!-- doctest: requires-env NAME -->`.
Keep a runnable block runnable. Do not add `skip` to make a test pass.

## Words

The docs use the structural rules of Simplified Technical English:

- Write short sentences: 20 words or fewer in an instruction, 25 in a description.
- Write one instruction in each sentence. Start it with the verb: "Run the tests."
- If a condition applies, write the condition first: "If the deploy fails, run `spinup rollback`."
- Use the active voice. Do not use contractions or semicolons.
- Use one name for one thing. The [glossary](../concepts.md#glossary) has the names.

Short sentences are not enough. Join the facts into an explanation.
Say why a step matters when the reader can get it wrong.

Write for the user of spinup, not for its maintainers:

- Do not cite ADR sections, milestones, or plan units in a guide. Link one ADR in "See also" if it helps.
- Do not name internal Go packages that the reader never types or imports.
- Name a file by the path the reader sees in their app, such as `api/cmd/api/main.go`.

## Formatting

- Use a table for options, keys, and defaults. Put the example column last.
- Use a numbered list for steps that must run in order.
- Use a callout for a warning that can lose data or break a deploy:

  ```markdown
  {: .warning }
  `spinup db reset` deletes every row in the development database.
  ```

  The site has `.note`, `.tip`, `.warning`, and `.important` callouts.
- Use sentence case in headings. Do not end a heading with a period.
- Link a command to its reference page the first time a page names it.

## Navigation

Every published page has front matter with `title`, `parent`, and `nav_order`.
The `parent` is the `title` of a section page:

| Section | Pages |
| --- | --- |
| Get started | install, first app, concepts |
| Build your app | resources, pages, auth, roles, mail, jobs, services, reports, audit |
| Deploy | deploy files, DigitalOcean, your own VM, infrastructure, CI |
| Operate | monitoring, backups, maintenance, data handling |
| Upgrade | upgrade spinup and the app, modules |
| Commands | one guide for each command group |
| CLI reference | generated by `spinup docs reference` |
| Policies | support, compatibility, Windows |
| Contributing | how to work on spinup |

Do not edit `docs/site/`. Run `spinup docs reference --out docs/site` after you change a command.
A command's examples come from the `Example` field of its cobra command.
