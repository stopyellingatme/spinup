# Mail

The `mail` module sends email from your app.
It gives you typed mailers, email templates, and a development inbox.
With the `auth` module, it also adds password reset.

```console
$ spinup new todo --module example.com/todo --modules ci,auth,mail --no-git --non-interactive
...
$ cd todo
$ spinup g mailer welcome name:string
Created 4, updated 0 files
Next: cd api && go test ./internal/mail/...
```

## Create a mailer

`spinup g mailer welcome name:string` creates one mailer.
The template fields (here `name`) become a typed Go struct.

| File | What it holds |
| --- | --- |
| `api/internal/mail/welcome_gen.go` | `WelcomeData` and `SendWelcome`. Do not edit this file. |
| `api/internal/mail/templates/welcome.subject.tmpl` | The subject. One line. |
| `api/internal/mail/templates/welcome.txt.tmpl` | The text body. Required. |
| `api/internal/mail/templates/welcome.html.tmpl` | The HTML body. |

The text and subject use `text/template`. The HTML uses `html/template`, which escapes the data.
The loader rejects a line break in a subject.
See [spinup g mailer](site/commands/generate-mailer.md) for the command.

## Send mail from a handler

`api/cmd/api/main.go` creates the mailers with `mailapp.New(pool)`.
Pass the value to your handler, and call the method of the mailer:

```go
err := mailers.SendWelcome(r.Context(), "ada@example.com", mail.WelcomeData{Name: "Ada"})
```

With the `jobs` module on, `SendWelcome` does not send at once.
It adds a `mail.send` job to the River `mail` queue, and a worker sends it. See "Background delivery" below.

## See mail in development

`spinup dev` starts Mailpit, a local inbox.
When `SMTP_URL` is not set in development, the mailers use `smtp://localhost:1025`.
Open `http://localhost:8025` to read the emails.

Outside development, an empty `SMTP_URL` selects the log transport.
It records delivery metadata and leaves out the message content.

## Send real mail

Set these variables in the environment of the API and the worker:

| Variable | Meaning | Default | Example |
| --- | --- | --- | --- |
| `SMTP_URL` | The server and the way to connect. | none | `smtp+starttls://apikey@smtp.example.com:587` |
| `SMTP_PASSWORD` or `SMTP_PASSWORD_FILE` | The password, or a file that holds it. | none | `/run/secrets/SMTP_PASSWORD` |
| `SMTP_TIMEOUT` | The limit for one delivery. | `10s` | `20s` |
| `MAIL_FROM` | The sender address. | `noreply@example.com` | `Todo <hello@example.com>` |

Choose the scheme of `SMTP_URL`:

| Scheme | Meaning |
| --- | --- |
| `smtp+starttls://user@host:587` | STARTTLS is required. |
| `smtps://user@host:465` | Implicit TLS. |
| `smtp://user@host:587` | With a user, STARTTLS is required. |

Neither TLS mode falls back to plaintext.
Do not put the password in the URL.

In development, you can put the variables in `.env`.

For a deployed app, store the password as a secret. A deploy puts it in `/run/secrets/SMTP_PASSWORD`.
Then add the other variables to the `api` service in `deploy/compose.yml`.
With the `jobs` module, add the same lines to the `worker` service, because the worker sends the mail.

<!-- doctest: skip -->
```console
$ printf '%s' 'the-smtp-password' | spinup secrets set --env production SMTP_PASSWORD
```

```yaml
services:
  api:
    environment:
      SMTP_URL: smtp+starttls://apikey@smtp.example.com:587
      SMTP_PASSWORD_FILE: /run/secrets/SMTP_PASSWORD
      MAIL_FROM: hello@example.com
```

{: .note }
Edit `deploy/compose.yml` itself. If you define the `api` service again in `deploy/compose.override.yml`, Compose stops with `services.api conflicts with imported resource`. See [Secrets](deploy/secrets.md) for `spinup secrets`.

## Background delivery

With the `jobs` module, a worker sends the mail.
The standard worker handles the `default` and `mail` queues, with ten concurrent jobs in each.
River retries a failed delivery up to ten times.

`spinup dev` and the deploy files start this worker for you.
To run it by hand, migrate first:

```sh
cd api
go run ./cmd/api migrate up
go run ./cmd/worker
```

For mail capacity of its own, run the API binary with `mail-worker`.
It takes only the `mail` queue, and River shares the jobs between the active workers.

```sh
go run ./cmd/api mail-worker
```

{: .note }
Protect the River tables. A queued message can hold a password reset link.

## Password reset

With `auth` and `mail`, the app has a reset flow:

1. The user opens `/reset` and enters an email.
2. The app mails a link to `/reset/[token]`.
3. The user sets a new password on that page.

The link uses `PUBLIC_ORIGIN`, which your app controls.
The reset page turns off caching and referrer disclosure.

You can call the routes yourself:

<!-- doctest: skip -->
```console
$ curl -i -H 'Content-Type: application/json' -d '{"email":"ada@example.com"}' http://localhost:8080/api/auth/reset/request
HTTP/1.1 202 Accepted
...
```

`POST /api/auth/reset/request` always answers 202 with an empty body.
The answer is the same for unknown accounts, invalid emails, and requests over the limit.
So nobody can learn which emails have accounts.
The app looks up the account and sends the email in a background queue, so the response time also hides it.

`POST /api/auth/reset/confirm` takes `{"token","password"}`.
The new password follows the registration rules.
A confirmation ends all sessions of the user, removes all reset tokens, and clears the login lockout.
The email never contains the password.

| Rule | Value |
| --- | --- |
| Requests for one email | 5 in 15 minutes |
| Requests for the whole app | 100 in 15 minutes |
| Token life | 1 hour, one use |
| Token storage | The database keeps only a SHA-256 hash of the 32-byte token. |

The limits count the normalized email, not the client address.
The limit for one email applies first, so repeated requests for one address cannot use up the app limit.
`auth.WithLockout` changes the limit for one email and the window of both limits.
The per-client rate limit also applies. See [Sign-in security](build/auth-security.md).

## Test mail

In a test, use `mail.Capture` as the transport and read the messages:

```go
cap := &kitmail.Capture{}
mailers := &mail.Mailers{Mailer: cap, From: "noreply@example.com"}

err := mailers.SendWelcome(ctx, "ada@example.com", mail.WelcomeData{Name: "Ada"})
// handle err
msg := cap.Messages()[0]
// msg.To == "ada@example.com"; msg.Subject, msg.Text, and msg.HTML hold the rendered mail.
```

`kitmail` is `github.com/stopyellingatme/spinup/kit/mail`.

## Reset routes in your own code

If you wire the kit yourself, call `Auth.ResetRoutes` with `auth.WithMailer`, `auth.WithResetURL`, and `auth.WithResetFrom`.
Install the auth middleware on these routes.
Use `auth.WithResetTemplates` for your own templates.
Without a mailer option, `ResetRoutes` registers no routes.
The generated `api/cmd/api/reset.go` does this for you.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| No email arrives in development | `spinup dev` is not running, or the worker is off. | Start `spinup dev`. Check `http://localhost:8025`. |
| No email arrives in production | `SMTP_URL` is empty, so the log transport is on. | Set `SMTP_URL`. |
| Mail stays in the queue | The worker does not run, or the migrations did not run. | Run `migrate up`, then the worker. |
| The delivery times out | The server is slow. | Raise `SMTP_TIMEOUT`. |
| `spinup g mailer` fails | The app has no mail module. | Run `spinup module add mail`. |
