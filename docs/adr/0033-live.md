# ADR 0033: Live data module

Status: accepted (owner, 2026-11-13)
Date: 2026-11-13
Amends: ADR 0003 (the long-request risk), ADR 0029 section 17 (push refresh), ADR 0031 sections 1.2 and 1.6 (no SSE)
Extends: ADR 0024 (roles), ADR 0028 (kit migration space), ADR 0029 (the module pattern and kit routes), ADR 0030 (API keys), ADR 0031 (the OTel pattern and the Caddy block)

## Context

On 2026-11-13 we compared spinup with corten, a Rust web framework of a co-worker.
Corten has SSE feeds: a snapshot, numbered patches, resume by cursor, and a Postgres outbox.
Spinup has the plumbing for a stream (`WithRequestTimeoutExempt`, `ResponseController`), but no feature that uses it.
A page in a generated app shows old data until the user reloads it.

A study of the code on 2026-11-13 found these facts:

- `kit/app/app.go:269` stops the server with `server.Shutdown` and runs the shutdown hooks after it. An open stream is an active connection, so `Shutdown` waits for it until the 20 s limit.
- `kit/app/options.go:27` makes `WithRequestTimeoutExempt` replace the earlier predicate. A second call removes the first one.
- `kit/devtools/devtools.go:119` has a `statusWriter` with no `Unwrap`. In dev (`config.Env == "dev"`) the writer chain loses `Flush`, so a stream does not flush.
- `http.Server.WriteTimeout` is the request timeout (30 s). `requestDeadline` clears the write deadline of an exempt request (`kit/app/deadline.go:22`).
- Generated resources are owner-scoped (`user_id`) or shared. A list is a page of at most 200 rows. A snapshot is a bounded database read.
- Kit migrations exist only with the `auth` module (ADR 0028). The highest kit number is `00010_billing.sql`.
- `auth` is refused in embed mode (`internal/modules/select.go:66`). A module that requires `auth` is refused in embed mode too.
- Caddy `encode` compresses `text/event-stream` with gzip when the response has no `Cache-Control: no-transform` (checked with Caddy 2.11.9 on 2026-11-13, see the appendix).
- The CSP of the web pack has `connect-src 'self'`. The browser reaches `/api/...` on the same origin, in dev through the Vite proxy and in production through Caddy.

The owner decided these points on 2026-11-13. They are binding:

1. The feature is an opt-in module `live`. It requires `auth`.
2. The wire format follows corten: a snapshot `{"epoch","seq","rows"}`, and an SSE stream of `patch` and `sync` events with a cursor `<epoch>-<seq>`.
3. Postgres is the only broker. Each API instance holds one `LISTEN` connection and polls every 5 s as a fallback. There is no NATS.
4. The hub holds a ring of encoded frames and no rows. The snapshot is a capped database read.
5. The route decides who may read a feed (a session or an API key). A stream ends after at most 15 minutes, so a revoked session stops there.
6. Flags still poll (ADR 0029). The MCP endpoint stays stateless (ADR 0031). Embed mode is out of scope.

## Decisions

### 1. Promise and limits

1.1. A client that holds a snapshot and a cursor sees every later committed change of the feed, in commit order, with no gap. It does this by `since` resume, or it gets a `sync` event and loads the snapshot again.
1.2. A patch has at-least-once delivery after a snapshot. An `upsert` replaces a row by ID. A `delete` removes a row by ID. Both are idempotent, so a repeat is safe.
1.3. `Publish` runs in the transaction of the write. If the transaction rolls back, nothing is published. If it commits, the patch is in the outbox and reaches every instance.
1.4. A write outside the handlers (a job, `psql`) publishes nothing. The doctor check `live-wired` warns about a feed that has no `Publish` call in the handlers (section 14).
1.5. The stream is outside the request deadline (`REQUEST_TIMEOUT`). It has its own limits: 15 minutes of age, a heartbeat, a write timeout, and stream counts (section 7).
1.6. Out of scope: WebSocket, presence, rows in the hub memory, a message broker, cross-feed transactions, a per-row access check on each patch, and embed mode (section 20).
1.7. Writers of one feed commit one after the other. `Publish` locks the row of the feed in `live_feeds` until the transaction ends. This is how the sequence has no gap. Two transactions that write to one feed wait for each other. An owner-scoped feed has one feed for each user, so the wait is rare. A shared feed on a table with many writes is a bottleneck. Call `Publish` last in the transaction, so the lock is short.

### 2. Dependencies

2.1. No new module. `kit/go.mod` has `github.com/jackc/pgx/v5 v5.11.0`, `go.opentelemetry.io/otel`, and the `metric` and `trace` packages (used by `kit/x/mcp`).
2.2. `kit/x/live` imports `kit/auth`, `kit/httpx`, and `kit/db`. It imports no other spinup package.
2.3. The generated app imports `github.com/stopyellingatme/spinup/kit/x/live` only. It uses the types of pgx that its handlers already import.

### 3. Kit changes in `kit/app` and `kit/devtools`

3.1. New option, in `kit/app/options.go`:

```go
// WithDrain adds a drain hook. Drain hooks run when shutdown starts, before the
// HTTP server stops. Use one to end long-lived responses, such as SSE streams.
// Hooks run in reverse option order and share one deadline of DrainTimeout.
// A hook must return when its context ends.
func WithDrain(hook func(ctx context.Context) error) Option

// DrainTimeout is the time that the drain hooks share.
const DrainTimeout = 5 * time.Second
```

3.2. The shutdown order of `serveListener` is now:

1. The context ends (SIGINT or SIGTERM), or `Serve` fails.
2. The drain hooks run, with the context `context.WithTimeout(context.WithoutCancel(ctx), min(DrainTimeout, ShutdownTimeout))`.
3. `server.Shutdown` runs with the shutdown context (default 20 s). It sees no live stream, because the drain hooks ended them.
4. The shutdown hooks run in reverse order, as before.

A drain hook error joins the problems of the shutdown. It does not stop the next step. With no drain hook, the order is the order of ADR 0003 and before.

3.3. `WithRequestTimeoutExempt` becomes additive. Each call adds a predicate. A request is exempt when any predicate returns true. A nil predicate adds nothing. The field `timeoutExempt func(*http.Request) bool` becomes `timeoutExempt []func(*http.Request) bool`. The doc comment says: "Each call adds a predicate. Predicates must support concurrent calls."

3.4. `statusWriter` in `kit/devtools/devtools.go` gets `func (w *statusWriter) Unwrap() http.ResponseWriter { return w.ResponseWriter }`. `http.NewResponseController` then finds `Flush` and `SetWriteDeadline` below it.

3.5. `kit/api/current.txt` gets the new lines for `WithDrain` and `DrainTimeout` (`SPINUP_GOLDEN_UPDATE=1 go test ./internal/apicompat`). The change is additive, so `TestKitAPI` accepts it after the update.

### 4. Kit API: package `kit/x/live`

The package is under `kit/x`, so its API can change before v1 and the API baseline does not list it.

```go
package live // import "github.com/stopyellingatme/spinup/kit/x/live"

// Key names one feed. A shared feed has the form "notes". An owner-scoped feed
// has the form "notes:42" (the name, a colon, and the user ID).
// The pattern is ^[a-z][a-z0-9_]{0,47}(:[0-9]{1,18})?$.
type Key string

func SharedKey(feed string) Key
func OwnedKey(feed string, userID int64) Key
func (k Key) Valid() error
func (k Key) Feed() string // the name without the scope, such as "notes"

// Op is the kind of a change.
type Op string

const (
	OpUpsert Op = "upsert" // replace the row with this ID, or add it
	OpDelete Op = "delete" // remove the row with this ID
	OpTouch  Op = "touch"  // the row with this ID changed: load it again
)

// Change is one change of a patch. ID matches ^[A-Za-z0-9_.:-]{1,64}$.
// Row is encoded with encoding/json when the change is published. A delete and a touch carry no row.
type Change struct {
	Op  Op
	ID  string
	Row any
}

func Upsert(id string, row any) Change
func Delete(id string) Change
func Touch(id string) Change

// Publish writes one patch to the feed in the transaction tx.
func Publish(ctx context.Context, tx pgx.Tx, key Key, changes ...Change) error

// Cursor is a position in a feed.
type Cursor struct{ Epoch, Seq int64 }

func (c Cursor) String() string             // "<epoch>-<seq>", for example "1731500000000-42"
func ParseCursor(s string) (Cursor, error)  // two decimal numbers of 1 to 18 digits, one "-" between them

// KeyFunc authorizes a request and names its feed. It returns ErrUnauthorized or
// ErrForbidden to refuse the request. Any other error is a server error.
type KeyFunc func(r *http.Request) (Key, error)

var (
	ErrUnauthorized = errors.New("live: a signed-in user is required")
	ErrForbidden    = errors.New("live: the user cannot read this feed")
)

// Hub holds the streams of one process.
type Hub struct{ /* unexported */ }

func New(pool *pgxpool.Pool, opts ...Option) (*Hub, error)
func (h *Hub) Start(ctx context.Context) error
func (h *Hub) Ready(ctx context.Context) error

func (h *Hub) Close(ctx context.Context) error
func (h *Hub) Command() func(ctx context.Context, args []string) error
func (h *Hub) Stream(key KeyFunc) http.Handler

// Snapshot returns the handler of the snapshot route of a feed.
func Snapshot[T any](h *Hub, key KeyFunc, load func(ctx context.Context, key Key, limit int) ([]T, error)) http.Handler

// IsStream reports whether r is a stream request: GET, a path that starts with
// "/api/live/", and a path that ends with "/live". Pass it to app.WithRequestTimeoutExempt.
func IsStream(r *http.Request) bool

// Prune deletes old patches and idle feeds.
type PruneOptions struct {
	Patches time.Duration // delete patches older than this; 0 means 1 hour
	Feeds   time.Duration // delete feeds with no patch and no update for this long; 0 means 30 days
}
type Pruned struct{ Patches, Feeds int64 }
func Prune(ctx context.Context, pool *pgxpool.Pool, o PruneOptions) (Pruned, error)

type Option func(*options)

func WithTracerProvider(tp trace.TracerProvider) Option      // default otel.GetTracerProvider()
func WithMaxStreams(n int) Option                            // default 2000
func WithMaxStreamsPerUser(n int) Option                     // default 8
func WithMaxStreamAge(d time.Duration) Option                // default 15 * time.Minute
func WithHeartbeat(d time.Duration) Option                   // default 15 * time.Second
func WithPollInterval(d time.Duration) Option                // default 5 * time.Second

func WithBootstrapLimit(n int) Option                        // default 4
func WithBootstrapWait(d time.Duration) Option               // default 2 * time.Second
func WithRetention(d time.Duration) Option                   // default time.Hour (the patch age that the hub prunes)
func WithIdleTTL(d time.Duration) Option                     // default 60 * time.Second
func WithWriteTimeout(d time.Duration) Option                // default 10 * time.Second
func WithSnapshotLimit(n int) Option                         // default 500
```

4.1. `New` validates the options and the pool (not nil). It does no I/O. A value of zero or less for a limit uses the default. A negative duration is an error with a `Try:` line.
4.2. `Publish` rules. It validates the key and the changes before it runs SQL. The limits are: 1 to 100 changes, an ID of 1 to 64 bytes that matches the pattern above, a row of at most 16 KiB after `json.Marshal`, and a patch of at most 64 KiB. A violation returns an `*Error` (section 15) and writes nothing. A row that is too large has the `Try:` line "publish live.Touch(id) instead".
4.3. `Publish` writes one patch for all its changes: one sequence number and one outbox row (section 5.3). A client gets all changes of one transaction in one `patch` event.
4.4. `Publish` has no `*pgxpool.Pool` form on purpose. A publish outside the transaction of the write would not be atomic with the data.
4.5. The cursor types are `int64`. The epoch is a time in milliseconds since 1970 (section 5.2). The value `0-0` means "the feed has no row yet". A cursor with the epoch 0 and the sequence 0 matches any epoch, and a replay from sequence 1 follows (section 7.6).
4.6. `Key.Valid` returns an error that names the pattern. `SharedKey` and `OwnedKey` do not validate. `Publish` and `Stream` do.
4.7. `IsStream` makes no allocation.

### 5. Database

5.1. The kit migration is `internal/templates/packs/live/files/api/db/kit/00011_live.sql` (class `seed`). The number 00011 is the next free kit number: `TestKitMigrationNumbers` accepts it, because the highest number is `00010_billing.sql`. The file is a shared file: only the main loop edits it. The full text:

```sql
-- +goose Up
-- spinup:safe
-- The live data module of ADR 0033. live_feeds holds the position of each feed.
-- live_outbox holds the patches of the last hour (the hub prunes it). An existing
-- migration never changes.
CREATE TABLE live_feeds (
    key text PRIMARY KEY CONSTRAINT live_feeds_key_check CHECK (key ~ '^[a-z][a-z0-9_]{0,47}(:[0-9]{1,18})?$'),
    -- The epoch is the creation time in milliseconds. A feed that is deleted and
    -- created again gets a larger epoch, so an old cursor never matches it.
    epoch bigint NOT NULL DEFAULT (extract(epoch FROM clock_timestamp()) * 1000)::bigint,
    seq bigint NOT NULL DEFAULT 0 CONSTRAINT live_feeds_seq_check CHECK (seq >= 0),
    updated_at timestamptz NOT NULL DEFAULT now()
) WITH (fillfactor = 70);

CREATE TABLE live_outbox (
    feed text NOT NULL REFERENCES live_feeds (key) ON DELETE CASCADE,
    seq bigint NOT NULL,
    changes jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (feed, seq)
);
CREATE INDEX live_outbox_created_at_idx ON live_outbox (created_at);

-- One NOTIFY for each feed in a statement. The payload is "<seq> <feed key>". A
-- notification is a hint: the hub reads the patch from live_outbox.
-- +goose StatementBegin
CREATE FUNCTION live_outbox_notify() RETURNS trigger
LANGUAGE plpgsql
SET search_path = pg_catalog, public, pg_temp
AS $$
DECLARE
    r record;
BEGIN
    FOR r IN SELECT feed, max(seq) AS seq FROM new_rows GROUP BY feed LOOP
        PERFORM pg_notify('spinup_live', r.seq::text || ' ' || r.feed);
    END LOOP;
    RETURN NULL;
END
$$;
-- +goose StatementEnd

CREATE TRIGGER live_outbox_notify AFTER INSERT ON live_outbox
    REFERENCING NEW TABLE AS new_rows
    FOR EACH STATEMENT EXECUTE FUNCTION live_outbox_notify();

-- +goose Down
DROP TRIGGER live_outbox_notify ON live_outbox;
DROP FUNCTION live_outbox_notify();
DROP TABLE live_outbox;
DROP TABLE live_feeds;
```

5.2. The epoch default uses `clock_timestamp()`. The kit never reads the clock to make an epoch. The command `live reset` (section 10) sets a new epoch with the same expression.
5.3. `Publish` runs this statement in the transaction (parameters: `$1` key, `$2` the JSON array of changes):

```sql
WITH f AS (
    INSERT INTO live_feeds AS f (key, seq) VALUES ($1, 1)
    ON CONFLICT (key) DO UPDATE SET seq = f.seq + 1, updated_at = now()
    RETURNING seq
)
INSERT INTO live_outbox (feed, seq, changes) SELECT $1, seq, $2::jsonb FROM f
```

The `ON CONFLICT` update locks the feed row until the transaction ends (decision 1.7). The sequence has no gap and follows the commit order. The statement trigger runs once, and `pg_notify` delivers the hint when the transaction commits. A rollback delivers nothing.
5.4. The wire form of a patch (the JSON in `changes`) is an array: `[{"op":"upsert","id":"7","row":{...}},{"op":"delete","id":"3"}]`. A change has the members `op`, `id`, and `row` (only for an `upsert`). Postgres stores the array as `jsonb`, which sorts the members and removes extra spaces. A client must not depend on the order of the members.
5.5. `Prune` runs two statements, each in batches of 10,000 rows until a batch is short:

```sql
DELETE FROM live_outbox WHERE (feed, seq) IN
    (SELECT feed, seq FROM live_outbox WHERE created_at < now() - $1::interval ORDER BY created_at LIMIT 10000);
DELETE FROM live_feeds f WHERE f.updated_at < now() - $2::interval
    AND NOT EXISTS (SELECT 1 FROM live_outbox o WHERE o.feed = f.key);
```

The hub calls `Prune` every 5 minutes with the options `Patches` = `WithRetention` and `Feeds` = 30 days. Every instance prunes. The deletes are safe to repeat. A concurrent `Publish` updates `updated_at`, so the second statement does not delete the feed.
5.6. The outbox is not unlogged. A crash must not lose a patch that a client may need.
5.7. The audit module does not audit these tables. They hold copies of rows for one hour, and the owner-scoped copy has the same access rule as the row.
5.8. A restore of a database backup can move `seq` back. A client with a cursor that is ahead of the feed gets a `sync` (section 7.6). A client with an older cursor that the new feed passes again would replay wrong patches. After a restore, run `api live reset --all --yes`. The backup guide names this step (section 18).

### 6. The hub

6.1. **Tracked feeds.** The hub holds a state for each feed that has at least one stream, or had one in the last `IdleTTL`. A notification or a poll result for an untracked feed is ignored. The first stream of a feed loads it (6.5).
6.2. **The ring.** The state of a feed holds a ring of encoded frames. A frame is the exact bytes of one `patch` event. The ring has at most `WithRing` patches (default 1,024). The hub also keeps the sum of all ring bytes under `WithRing` bytes (default 8 MiB): when the sum is over the limit, the hub drops the whole ring of the idle feeds (feeds with no stream), the one that has been idle the longest first. If the sum is still over the limit, it drops the oldest patches of the largest ring, but it keeps at least 32 patches. A patch is at most 64 KiB, so one patch always fits. The ring is a cache of `live_outbox`: a dropped ring loads again from the table.
6.3. **Encode once.** The hub encodes a patch one time, when it reads it from the table. All streams of the feed write the same `[]byte`. The write to a client makes no copy and no allocation.
6.4. **Reader positions.** A stream does not have a queue. It holds the sequence of the next frame (`next`) and a wake channel with a buffer of 1. When a patch arrives, the feed appends the frame to the ring and does a non-blocking send on each wake channel. The stream then reads the frames from `next` to the head in one batch. A slow client does not use memory: it only falls behind in the ring. When `next` is older than the oldest frame of the ring, the stream sends `sync` with the reason `slow` and ends (section 7.8).
6.5. **Load of a feed.** The first stream of a feed runs this load, under a bootstrap slot (6.9), in a read-only transaction with the isolation `REPEATABLE READ`:

```sql
SELECT epoch, seq FROM live_feeds WHERE key = $1;
SELECT seq, changes::text FROM live_outbox WHERE feed = $1 ORDER BY seq DESC LIMIT $2;  -- $2 is the ring size
```

The hub encodes the rows, puts them in the ring in ascending order, and sets the head to the `seq` of the first statement. A feed with no row has the epoch 0 and the head 0. If the ring does not reach down to `seq - rows + 1` (a pruned row), the ring starts at its oldest row. Other streams of the feed wait for the load to end (they wait on a channel, not on the bootstrap slot).
6.6. **Fetch.** A notification marks a feed dirty. A fetch worker reads the new patches:

```sql
SELECT epoch, seq FROM live_feeds WHERE key = $1;
SELECT seq, changes::text FROM live_outbox WHERE feed = $1 AND seq > $2 ORDER BY seq LIMIT 256;  -- $2 is the head
```

It repeats the second statement while a batch is full. The hub has 4 fetch workers. One feed has at most one fetch at a time, and a mark during a fetch runs the feed again. The rows have no gap (decision 1.7). If the epoch differs from the epoch of the ring, or `seq` is below the head, or a row is missing, the hub resets the feed: it drops the ring, sets the new epoch, and wakes each stream with the state `reset`. The streams send `sync` (reason `reset`).
6.7. **LISTEN.** `Start` opens one dedicated connection with `pgx.ConnectConfig`. The config is `pool.Config().ConnConfig.Copy()` with `Tracer` set to nil. The connection is not part of the pool, so it does not use a slot of `DATABASE_MAX_CONNS`. It runs `LISTEN spinup_live`. The loop is:

1. `WaitForNotification` with a context of `PollInterval` (default 5 s).
2. A notification: parse `"<seq> <key>"`, mark the feed dirty if it is tracked, and read the next notification with no wait.
3. A timeout (`errors.Is(err, context.DeadlineExceeded)` or `pgconn.Timeout(err)`): run `conn.Ping` (a dead connection fails here), then run the poll (6.8). The connection stays in use (claim a in the appendix).
4. Any other error: close the connection, wait with a backoff of 1 s to 30 s with jitter, open it again, run `LISTEN`, and run the poll at once to catch up.

6.8. **Poll.** The poll runs `SELECT key, epoch, seq FROM live_feeds WHERE key = ANY($1)` for the tracked keys (in chunks of 500). It marks a feed dirty when its epoch differs from the ring or its `seq` is above the head. One query for each tick covers all feeds. A patch that the poll finds and the notification missed adds to the metric `live.poll.recovered`.
6.9. **Bootstrap slots.** A semaphore with `WithBootstrapLimit` slots (default 4) bounds the loads of 6.5 and the snapshot reads of section 7.3. A request waits for a slot at most `WithBootstrapWait` (default 2 s). Then it answers 503 with `Retry-After: 2`. The slot limit protects the pool when all clients reconnect at one time after a deploy.
6.10. **Lifecycle.**

- `Start(ctx)` opens the LISTEN connection (a failure logs a warning and the loop retries), starts the loop, the fetch workers, and the janitor (it ends idle feeds after `IdleTTL`, checks ring bytes every 15 s, and calls `Prune` every 5 minutes). A second call returns an error. `ctx` ends the loops.
- `Ready` returns an error before `Start` and after `Drain` begins. Otherwise it returns nil. A lost LISTEN connection is not a readiness failure, because the poll covers it. The `db` readiness check covers the database.
- `Drain(ctx)` is in section 7.9.
- `Close(ctx)` stops the loops, closes the LISTEN connection, and waits for the workers, subject to `ctx`. It is safe to call without `Start` and twice.

6.11. **The `Hub` struct** (file `hub.go`, unit LV3) has at least these fields, which the stream code of unit LV4 uses: `pool *pgxpool.Pool`, `opts options`, `m *metrics`, `mu sync.Mutex`, `feeds map[Key]*feed`, `ringBytes int64`, `boot chan struct{}` (the bootstrap slots), `drainCh chan struct{}` (closed by `Drain`), `streams int` and `perUser map[int64]int` (under `mu`), `wg sync.WaitGroup` (open streams), and `state` (new, started, draining, closed). The methods that unit LV3 provides for unit LV4 are `acquire(ctx, key) (*feed, error)` (find or load a feed, count one reference), `release(f *feed)` (drop a reference and set `idleSince`), `slot(ctx) (release func(), err error)` (a bootstrap slot), and `admit(userID int64) (release func(), err error)` (the stream counts of section 7.5).

```go
func (h *Hub) readCursor(ctx context.Context, key Key) (Cursor, error) // the first statement of decision 7.3
```

6.13. An `append` that is a gap (`seq` is not `head+1`) returns `appendGap`, and the hub resets the feed (decision 6.6). A stale epoch (`epoch` is below the epoch of the ring) returns `appendStale`, and the hub ignores the patch.

### 7. HTTP: snapshot and stream

7.1. The routes of one feed are `GET /api/live/<feed>` (the snapshot) and `GET /api/live/<feed>/live` (the stream). Both are under `/api/`, so Caddy sends them to the Go API. Both pass the auth middleware and the API key middleware. A read key may call them (a GET). Each connect counts as one request of the key plan.
7.2. The routes are kit routes. They are not in the app OpenAPI document. The document feeds oapi-codegen with `strict-server: true`, and the generated resource server asserts `gen.StrictServerInterface`. A path for a route that no generated code implements would stop the app build. SSE is not an operation that the strict server can express. ADR 0029 decision 8.1 (the flags routes) and ADR 0032 (the billing routes) made the same choice. The web helper calls the routes with `fetch` (section 12), so the generated client has no operation for them either. `client-drift` and `openapi-drift` stay silent.
7.3. **Snapshot.** `Snapshot[T]` returns a handler. It does these steps:

1. Call `key(r)`. A refusal answers as in section 8.
2. Take a bootstrap slot (6.9).
3. Read the cursor: `SELECT epoch, seq FROM live_feeds WHERE key = $1` on the pool. No row gives `0, 0`.
4. Call `load(ctx, key, limit+1)`, with `limit` = `WithSnapshotLimit` (default 500). `load` runs after step 3. So the rows are at least as new as the cursor, and the patches after the cursor replay in order (decision 1.2).
5. Answer `200`, `Content-Type: application/json`, `Cache-Control: no-store`, with `{"epoch":E,"seq":N,"rows":[...]}`. If `load` returned more than `limit` rows, cut the list to `limit` and add `"more":true`. The member `more` is absent otherwise. `rows` is `[]` and never `null`.

A `load` error answers 503 with `Try: retry the request later` and a log line at error level. The handler uses `encoding/json` (v1).
7.4. **Stream request.** `GET /api/live/<feed>/live?since=<cursor>`. `since` is optional. The header `Last-Event-ID` has the same meaning when `since` is absent. A `since` that is not a cursor answers 400. A request with no `since` starts at the head of the feed.
7.5. **Checks, in this order:**

1. The hub is draining: 503, `Retry-After: 1`, "The server is shutting down. Try: connect again."
2. `key(r)`: `ErrUnauthorized` gives 401 ("A signed-in user is required. Try: sign in, then connect again."), `ErrForbidden` gives 403 ("Your role cannot read this feed. Try: sign in with an account that has a required role."), and another error gives 500 with a log line.
3. `Key.Valid` fails: 500 with a log line (a programming error in the route).
4. The cursor: 400, "The since cursor is not valid. Try: pass the cursor of the snapshot, such as 1731500000000-42, or omit since."
5. The stream counts: the user is `auth.UserFrom(r.Context())` (ID 0 for a feed with no user). More than `WithMaxStreamsPerUser` streams for the user gives 429 with `Retry-After: 5` ("This account has N open live streams. Try: close another tab, then connect again."). More than `WithMaxStreams` streams in the process gives 503 with `Retry-After: 5` ("The server has the most live streams that it allows (N). Try: connect again in a few seconds."). The counts are atomic: a slot is taken before the load and released when the stream ends.
6. `acquire` the feed (it may load it under a bootstrap slot). A failed slot gives 503 with `Retry-After: 2` ("The server is loading other feeds. Try: connect again in a few seconds."). A database failure gives 503 ("The feed could not load. Try: retry the request later.").

Each problem body is `application/problem+json` (`httpx.WriteProblem`). The answer has no `text/event-stream` content type.
7.6. **Resume.** After the checks, the stream decides one of these:

| Case | Condition | Result |
|---|---|---|
| Start at the head | no `since` | `ready` (resumed false), then patches from `head+1` |
| Resume | `since.Epoch` equals the epoch of the feed (or `since` is `0-0` and the feed has an epoch), `since.Seq <= head`, and the ring holds every patch from `since.Seq+1` to the head | `ready` (resumed true), then the patches from `since.Seq+1` |
| Empty | the feed has no row (epoch 0), and `since` is `0-0` | `ready`, then patches from 1 |
| Epoch | `since.Epoch` differs from the epoch of the feed (and `since` is not `0-0`) | `sync` with the reason `epoch`, then the stream ends |
| Ahead | `since.Seq > head` | `sync` (reason `ahead`) |
| Gap | the ring does not hold `since.Seq+1` | `sync` (reason `gap`) |

7.7. **Frames.** The response has the status 200 and these headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, and `X-Accel-Buffering: no`. The value `no-transform` stops the Caddy `encode` directive from compressing the stream. The stream flushes the headers at once. Each event has this form (UTF-8, `\n` line ends, one blank line after the event):

```
event: ready
id: 1731500000000-42
data: {"epoch":1731500000000,"seq":42,"resumed":true}

event: patch
id: 1731500000000-43
data: {"epoch":1731500000000,"seq":43,"changes":[{"op":"upsert","id":"7","row":{"id":7,"body":"x"}}]}

event: sync
data: {"epoch":1731500000000,"seq":43,"reason":"gap"}

event: bye
data: {"reason":"age"}

: ping

```

- `ready` is the first event of a stream that opens. It tells the client that the stream is open and gives the head cursor, also on a resumed stream. A client keeps the cursor of the last patch that it got. When the resume check fails (the reasons `epoch`, `ahead`, and `gap`), the stream sends `sync` as its first and only event, with no `ready`. For an empty feed, the `id` of `ready` is `0-0`.
- `patch` is one outbox row. The `id` is the cursor after the patch. The data is JSON on one line, with no newline inside.
- `sync` means: the history from your cursor is not available. The stream ends after it. The client loads the snapshot and connects again. The reasons are `epoch`, `ahead`, `gap`, `slow`, and `reset`.
- `bye` means: the server ends the stream and the cursor is still good. The client connects again with its last cursor. The reasons are `age` and `drain`.
- `: ping` is a comment. The hub sends it every `Heartbeat` (15 s) when the stream is idle. It is one shared byte slice.

7.8. **Backpressure.** Each write sets `SetWriteDeadline(now + WriteTimeout)` (default 10 s) on the `http.ResponseController`. A write error or timeout ends the stream with the end reason `write`. A stream whose `next` falls out of the ring gets `sync` (reason `slow`) and ends. A stream never holds more than the ring of the feed. No queue grows.
7.9. **Age and drain.**

- A stream ends with `bye` (reason `age`) at a random age between 80 percent and 100 percent of `MaxStreamAge` (default 15 min). The jitter spreads the reconnects. A revoked session or a deleted user stops at that time at the latest, because the next connect runs the auth middleware again.
- `Drain(ctx)` sets the state `draining` and closes `drainCh`. Each stream writes `bye` (reason `drain`) and returns. `Drain` returns when no stream is open, or with `ctx.Err()` when the context ends first. With no stream it returns at once. New stream requests get 503 (7.5).

7.10. The handler never writes after it returned. The panic of a handler is the panic of any handler: `httpx.Recover` logs it.
7.11. A stream is outside `REQUEST_TIMEOUT` because the app passes `IsStream` to `WithRequestTimeoutExempt`. The exempt branch also clears the write deadline, and the stream sets its own.

### 8. Authorization

8.1. The route decides. `KeyFunc` runs on each request. It reads `auth.UserFrom(r.Context())`, which is set for a cookie session and for an API key (ADR 0030). It checks the role, and it returns the key that names the data the user may read.
8.2. For an owner-scoped resource the key is `OwnedKey(feed, user.ID)`. The user never names the scope, so one user cannot read the feed of another user. For a shared resource the key is `SharedKey(feed)`.
8.3. Authorization runs at connect. A role change or a revoked key takes effect at the next connect, after 15 minutes at most. A patch carries a row that the user may read when the stream opened. This is the accepted cost of the design. The docs name it (section 18).
8.4. A key that has the scope `read` may open a stream. The key quotas count the connect.
8.5. The snapshot and the stream of one feed use the same `KeyFunc`.

### 12. Web helper

12.1. Files: `web/src/lib/live.core.ts` (no Svelte, no SvelteKit import, so a test can run it), and `web/src/lib/live.svelte.ts` (the runes wrapper). Both are managed. Both work with the two client variants (openapi-fetch and heyapi), because they call `fetch` and do not use the generated client. The base URL is empty: the browser calls the current origin, where the Vite proxy (dev) or Caddy (production) sends `/api` to Go. The CSP `connect-src 'self'` allows it.
12.2. **Why `fetch` and a stream reader, and not `EventSource`:** `EventSource` cannot read a non-200 answer. It hides the status and the `Retry-After` header, and it retries a 401 forever. It cannot send a header, so it cannot pause when the tab is hidden without losing the cursor. It reconnects at its own pace with no jitter. `fetch` gives the status, the headers, an `AbortController`, and a reader of the body. The cost is a small SSE parser (about 60 lines).
12.3. **Core API** (`live.core.ts`):

```ts
export type LiveStatus = 'connecting' | 'live' | 'reconnecting' | 'paused' | 'unauthorized';
export type Change<T> = { op: 'upsert'; id: string; row: T } | { op: 'delete'; id: string } | { op: 'touch'; id: string };
export type Patch<T> = { epoch: number; seq: number; changes: Change<T>[] };
export type Cursor = { epoch: number; seq: number };
export interface LiveClientOptions<T> {
	feed: string;                       // the feed name, such as "notes"
	fetch?: typeof fetch;               // default globalThis.fetch
	getCursor: () => Cursor | null;     // null: start at the head
	onReady: (cursor: Cursor, resumed: boolean) => void;
	onPatch: (patch: Patch<T>) => void;
	onSync: (reason: string) => void;   // the owner loads the snapshot and calls resume
	onStatus: (status: LiveStatus) => void;
	random?: () => number;              // default Math.random, for tests
	setTimer?: typeof setTimeout;       // for tests
	now?: () => number;
}
export class LiveClient<T> {
	constructor(options: LiveClientOptions<T>);
	start(): void;
	stop(): void;
	pause(): void;       // abort the stream and keep the cursor
	resume(): void;      // connect again with the cursor (jitter 0 to 500 ms)
}
export function parseCursor(s: string): Cursor | null;
export function backoff(attempt: number, random: () => number): number; // milliseconds
export function parseSSE(): TransformStream<Uint8Array, { event: string; id: string; data: string }>;
```

12.4. **Connect and resume.** The client calls `fetch('/api/live/<feed>/live' + (cursor ? '?since=' + cursor : ''), { credentials: 'same-origin', headers: { Accept: 'text/event-stream' }, signal })`. It reads the body with `TextDecoderStream` and the SSE parser. A comment line counts as activity.
12.5. **Events.**

- `ready`: set the status `live`, reset the attempt count, and call `onReady` (the cursor of the event, and `resumed`).
- `patch`: call `onPatch`, and keep the cursor of the patch. A patch whose epoch differs from the cursor epoch (and the cursor epoch is not 0) is a bug: the client calls `onSync('epoch')`.
- `sync`: stop the stream, drop the cursor, and call `onSync(reason)`. The owner loads the snapshot (or refreshes the page) and calls `start()`.
- `bye`: close the stream, keep the cursor, and connect again after a random time of 0 to 1 s (reason `age`) or 0.5 to 3 s (reason `drain`).

12.6. **Reconnect.** The delay of attempt `n` (from 0) is `random() * min(30000, 1000 * 2^n)` milliseconds, at least 250. The attempt count resets at `ready`. A stream with no byte for 40 s (the server sends a heartbeat every 15 s) is aborted and counts as a failure. A 503 or 429 answer waits `max(Retry-After seconds * 1000, backoff)` plus the jitter. Any other network error or status of 500 and above backs off the same way. A 400 answer drops the cursor and connects again after the backoff.
12.7. **401 and 403.** A 401 stops the client, sets the status `unauthorized`, and calls `onSync('unauthorized')`. The wrapper then runs `invalidateAll()` one time, so the page `load` functions see the 401 and run the redirect of the app. A 403 stops the client, sets the status `unauthorized`, and does not retry.
12.8. **Hidden tab.** On `visibilitychange` to hidden, the wrapper starts a timer of 60 s. If the tab is still hidden after it, the wrapper calls `pause()` (status `paused`). On visible, it clears the timer and calls `resume()` when it paused. A resume uses the cursor, so the result is either a replay or one `sync`. The events `offline` and `online` pause and resume in the same way.
12.9. **One stream for each feed.** The wrapper keeps a module-level registry: one `LiveClient` for each feed name in the tab, with a count of the users. The last user stops it. A page with two components that use the feed `notes` opens one connection. A tab uses at most one stream for each feed.
12.10. **Svelte API** (`live.svelte.ts`):

```ts
export interface LiveRefreshOptions {
	debounceMs?: number;                     // default 200
	maxWaitMs?: number;                      // default 2000
	invalidate?: string | (() => unknown);   // default: invalidateAll()
}
export interface LiveState { readonly status: LiveStatus }

/** Call during component initialization. It refreshes the page data on each patch. */
export function liveRefresh(feed: string, options?: LiveRefreshOptions): LiveState;

export interface LiveListOptions<T extends { id: number | string }> {
	initial?: T[];                           // rows from the load function: skip the first snapshot request
	sort?: (a: T, b: T) => number;           // default: keep server order, append new rows
	limit?: number;                          // default 500: drop the rows above it after an upsert
}
export interface LiveList<T> {
	readonly rows: T[];
	readonly status: LiveStatus;
	readonly more: boolean;                  // the snapshot was cut
	refresh(): Promise<void>;                // load the snapshot again
}
export function liveList<T extends { id: number | string }>(feed: string, options?: LiveListOptions<T>): LiveList<T>;
```

12.11. `liveRefresh` is a thin layer: it creates or joins the client of the feed, and each patch (and each `ready` that has no cursor) schedules a debounced refresh (the trailing call, at most `maxWaitMs` after the first patch). It uses `$effect` to start and to stop. On the server (SSR) the effect does not run, so it does nothing. A `ready` with `resumed = false` also schedules one refresh, because a start at the head cannot know the changes between the page load and the connect.
12.12. `liveList` loads `GET /api/live/<feed>` (the snapshot), keeps `rows` in `$state`, connects with the cursor of the snapshot, and applies `upsert` and `delete` by `String(id)`. A `touch` and a `sync` call `refresh()`. A failed snapshot sets the status `reconnecting` and retries with the backoff. `liveList` is for hand-written pages. The generated pages use `liveRefresh`, because their `load` functions already fetch the page with the right filters.
12.13. The tests (`live.core.test.ts`, vitest, no DOM): the SSE parser with chunks that split a line, a UTF-8 character, and an event; `parseCursor`; `backoff` bounds; resume with `since`; `sync` calls `onSync` and drops the cursor; `bye` keeps the cursor; 401 stops; 503 with `Retry-After`; the idle abort at 40 s (fake timers); `pause` and `resume`.

13.3. **The feed file** (`api/internal/live/<plural>.go`). The marker line is `// spinup:live-feed <plural> register<Plural>Feed` on the line before the function. The regular expression is `^// spinup:live-feed ([a-z][a-z0-9_]{0,47}) (register[A-Z][A-Za-z0-9]*)$`. The file:

13.5. **Why `g live` does not edit the handlers of an existing resource.** The handler file is a scaffold file that the owner may have changed. A text edit of Go code is fragile. `g audit` made the same choice (it prints the `audit.InTx` lines). The doctor check `live-wired` finds the missing `Publish` (section 14).

13.7. **`ExistingSpec`.** Claim d (appendix): `resource.ExistingAuditSpec(root, target, flags)` (`internal/gen/resource/audit.go:167`) returns `(Spec, isResource bool, error)` with `Name`, `Owned`, `Shared`, and `Roles` (the roles of the `Get` guard, read by `getHistoryRoles`). ### 14. Doctor check `live-wired`

`internal/doctor/livewired` (`Scope: doctor.Local`, `Quick: true`). The pattern is `internal/doctor/mcpwired/check.go`. It skips when the lock has no `live` pack ("no live module"). It parses `api/cmd/api/main.go` with `go/ast`. Each failure is a `Warn` that names the missing line and ends with a `Try:` line. It requires:

1. the import of the app live package (path suffix `/api/internal/live`) and the import of `kit/x/live`;
2. a call of `kit/x/live.New` whose result is bound to a variable, and a `.Start(` call on it;
3. inside `app.New(`: a call of `Routes` of the app live package, `app.WithRequestTimeoutExempt(` with the argument `<kitlive>.IsStream`, `app.WithDrain(` with `<hub>.Drain`, and `app.WithShutdown(` with `<hub>.Close`;
4. the file `api/db/kit/00011_live.sql` exists (the Try line: `spinup upgrade` or `spinup module add live`).

Then, for each feed marker in `api/internal/live/*.go` (use `internal/gen/live.ScanFeeds`), it checks:

5. `api/internal/live/feeds_gen.go` calls the `register` function of the marker (else: run `spinup g live <resource> --force`, or fix the file; the managed file is rewritten by the generator);
6. some non-test Go file under `api/internal` outside `api/internal/live` calls `Publish` of `kit/x/live` and calls `OwnedKey` or `SharedKey` with the feed name as the first argument. If none does, the status is `Warn` with the message "the feed notes has no Publish call. A write that does not publish does not reach the clients." and the Try line "add live.Publish to the handlers of the resource (see docs/build/live.md), or remove the feed".

All checks pass: `OK` with the message "live wiring is present". The check runs no SQL.

### 15. Errors

15.1. Every user-facing error of the kit says what failed and why, and ends with a `Try:` line (the rule of CLAUDE.md). This covers the problem bodies of section 7 and the command errors of section 10.
15.2. `*live.Error` (`Error() string`, `Unwrap() error`) is the type of the errors that `Publish`, `Prune`, and `Command` return. The text form is `live: <what failed>: <why>\nTry: <fix>`. A PostgreSQL error with the code `42P01` (undefined table) uses the Try line "run the migrations (spinup db migrate up) with the live module on (spinup module add live)".
15.3. A stream cannot send a `Try:` line after it has sent a 200. The events of section 7.7 have a `reason` code, and the web helper maps it to an action.

### 16. Upgrade of existing apps

`spinup module add live` adds the pack to an app that has `auth`. The migration is a seed file, so `spinup db migrate up` runs it. ### 20. Embed mode

Embed mode is out of scope. `live` requires `auth`, and `auth` is refused in embed mode. So `spinup new --frontend-mode embed --modules auth,live` and `spinup module add live` on an embed app fail with the existing message ("cannot use auth in embed mode ... Try: use --frontend-mode node"). The kit package itself works in any Go server. The pack files do not use a `when` guard. The change to `app.WithDrain` and to the exempt predicate helps embed apps with their own streams.

> Amended 2026-11-25 by ADR 0039 section 10: the `live` module works in embed mode. The browser helper stops every stream before sign-out and uses scoped invalidation. Section 10.2 and section 10.5 of ADR 0039 hold the contract. The text above is the historical decision.

### 21. Changes from the review (2026-11-14)

A review of the code found eight defects. These decisions replace the text above where they differ.

21.1. **`MarkMore`.** `func MarkMore(ctx context.Context)` is part of the kit API. A load function calls it when it returns fewer rows than the source holds. Step 5 of decision 7.3 becomes: if `load` returned more than `limit` rows, or called `MarkMore`, cut the list to `limit` and add `"more":true`. The generated loader calls `kitlive.MarkMore(ctx)` when `Total > len(Items)`, because the list of a resource has at most 200 rows.
21.2. **Reset.** The reset of decision 6.6 clears the ring, loads it again, marks each stream, and wakes it under one hold of the feed lock. A stream that joins during a reset never sees an empty ring.
21.3. **Write deadline.** After a successful flush the stream clears the deadline (`SetWriteDeadline(time.Time{})`). With HTTP/2 an armed deadline resets an idle stream, also with no pending write.
21.4. **Shared feed in the web helper.** `live.core.ts` exports `SharedFeed`, `FeedSubscriber` (with `catchUp`), and `FeedMembership`. Each subscriber keeps its own position. The stream starts at the oldest position that a subscriber needs, and it restarts only for an older cursor or a newer epoch. A subscriber gets only the patches after its position. A `liveRefresh` that joins a feed that is already open schedules one refresh.
21.5. **Destroy.** `spinup destroy resource` rebuilds `feeds_gen.go` through `resource.PlanLiveDestroy`, so the registration of the removed feed goes away.
21.6. **Metrics.** `func (m *metrics) unobserve()` removes the callback of `observe`. `Close` calls it. Evicted feeds leave the notification map.
21.7. **Logger.** The default logger of the hub reads `slog.Default()` at each log call. The generated `main.go` builds the hub before `app.New` installs the JSON logger.

## Not done, with the reason

| Item | Reason |
|---|---|
| NATS or another broker | Postgres already holds the data and the commit order. A second system doubles the operations. LISTEN and the poll are enough for one VM and a few replicas. |
| WebSocket, presence | SSE covers server-to-client push. Presence needs state that the hub does not hold. |
| Rows in the hub memory (corten's model) | Spinup resources are owner-scoped and paginated. A snapshot is a capped read. A ring of frames is small and does not need a per-user row set. |
| A row access check on each patch | The patch goes to the streams of one key, and the key is owner-scoped. A shared feed with a role guard is checked at connect. A per-patch check would need a policy language. |
| An OpenAPI path for the routes | The strict server cannot implement SSE, and a kit route with no implementation stops the build (decision 7.2). |
| `EventSource` | No status, no `Retry-After`, no jitter, no pause (decision 12.2). |
| Cross-tab sharing (`BroadcastChannel`) | One stream for each feed and tab is enough. The per-user limit is 8. |
| `g live` rewrites the handlers of an existing resource | A text edit of an owned file is fragile. The generator prints the lines and the doctor check finds the gap (decision 13.5). |
| A feed for a table with no generated resource | The feed file is a scaffold. An owner copies it. A generator for any table needs a model of the table. |
| A `[live]` table and a drift check | A feed is Go code with a marker. There is nothing to compare. |
| Publish from a job or from SQL | A job may call `live.Publish` in its transaction. A trigger-based publish for `psql` writes is a later ADR. |
| A Playwright test for two browsers | The gate checks the wire with curl. The dogfood check (the milestone verification) shows the two-browser case by hand. |
| `tools/list`-like change notifications for MCP | MCP stays stateless (decision 6). |
| A restore that fixes epochs by itself | A backup does not know the clients. `live reset --all` is the step, and the backup guide says so. |

## Consequences

- A generated app can show live data with one module and one flag on `g resource`.
- Each write of a live resource adds one statement (the feed update and the outbox insert) in its transaction, and one lock on the feed row until commit.
- A deploy with live clients takes the full 10 s drain (ADR 0003 amendment). All clients then connect again at one time. The client jitter, the heartbeat, and the limit of 4 bootstrap loads reduce the effect. `scripts/perf/livegen` measures it.
- Each API instance holds one more database connection (the LISTEN connection), and a database restart ends it. The poll covers a gap of 5 s.
- The outbox holds one hour of row copies. The copy has the same access rule as the row.
- A revoked session can read for 15 minutes at most.
- A write outside the handlers publishes nothing. `live-wired` warns about a feed with no `Publish`.
- Kit `kit/x/live` can change before v1.
